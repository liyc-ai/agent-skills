# 全仓库代码审查

目标是回答三个问题：代码是否整洁，是否存在真实 bug，功能、文档和示例是否完备。
审查不是把文件读一遍然后列感想，而是先建立可验证的基线，再用测试和最小复现证明
问题，最后用尽量小的改动修掉它。

## 先确定什么算做完

开工前用几句话写下这次的验收范围，至少包括：

- 覆盖哪些目录、命令、文档和示例；哪些明确不看。
- 以什么为基线：现有测试、lint、类型检查、构建、示例脚本，以及 README 里承诺的
  行为。
- 修到什么程度：只报告，还是顺手修掉高置信度问题；文档和示例是否一起对齐。
- 哪些验证需要联网、真实数据、外部服务或人工操作，默认跳过还是必须执行。

如果用户只说了“review 一下”，默认做只读审查加高置信度修复，不改架构、不提交、
不推送。范围真的不清楚时先问，不要靠猜。

## 什么时候用，什么时候不用

适合：整个仓库的质量审查、接手陌生代码库、发布前检查、路线图完成后的完备性
审计、检查“代码能跑但不知道哪里会炸”。

不适合：只看一个 PR/diff（用 diff review）、只做安全审计（用 security review）、
只做性能优化、只跑一次格式化。仓库很小且只有一两个文件时，直接读代码即可，不必
套完整流程。

## 核心原则

1. 证据优先。读代码只能提出假设，不能证明 bug。能用测试、脚本、命令复现的，
   先复现；不能复现的，在报告里标成“未验证的怀疑”。
2. 先基线后改动。先跑一遍原有检查并记录结果，再动代码。否则修完之后分不清是
   新问题还是旧问题。
3. 最小改动。一次只改一类问题，能加一个测试就不重构整个模块。审查阶段不做
   顺手架构升级。
4. 修 bug 必须留回归测试。至少覆盖触发条件；边界 bug 要覆盖边界两侧。
5. 文档和示例属于完备性，不是附属品。README 里的命令、参数、输出路径、数据
   前提，都要和代码对得上；教程要能从干净环境跑通。
6. 不伪造验证。没跑就说没跑，没网就说没网。不要把“看起来应该没问题”写成
   “已验证”。
7. 同一件事连续两次尝试没有进展，停下来汇报假设、试过什么、卡在哪里，把下一步
   交给用户。不要用更多随机改动掩盖卡住的事实。

## 流程

### 0. 侦察，不急着读细节

先看仓库形状和当前状态：

```bash
pwd
git status --short
git log --oneline -5
find . -maxdepth 2 -type f | sort | sed -n '1,160p'
```

确认包管理器、入口、测试目录、CI、文档、示例和数据目录。读 `README`、
`AGENTS.md`/`CLAUDE.md`、`Makefile`/`package.json`/`pyproject.toml`，把项目声称
能做的事情列成一张契约清单。清单不用长，十条左右，例如“一条命令能跑通回测”、
“配置文件支持某几个字段”、“示例不联网也能跑”。

同时检查明显风险：源码目录是否被 `.gitignore` 误伤、是否有真实密钥/持仓/个人
数据、是否有生成物混进版本库。

### 1. 跑基线

按仓库自己的入口跑，不要自创命令：

```bash
# 有 Makefile 时优先
make check
make test

# Python 常见组合
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest -q

# Node / Rust / Go 常见组合
npm test && npm run lint && npm run build
cargo test && cargo clippy -- -D warnings
go test ./... && go vet ./...
```

记录每条命令的结果：通过、失败、跳过、需要网络、耗时异常。测试全绿也要看测试
数量和跳过原因；只有几个测试、或者关键模块根本没有测试，本身就是发现。

跑一个最小可运行路径：示例脚本、CLI `--help`、构建产物、demo。它比读十遍入口
代码更能暴露环境问题。

### 2. 画出契约和依赖方向

对每个主要模块回答：

- 它对外承诺什么输入、输出、单位和副作用？
- 它依赖谁，谁依赖它，有没有反向依赖或循环？
- 哪些状态会跨调用保留，哪些应该无状态？
- 哪些错误应该抛出，哪些应该跳过并记录？
- 配置、默认值和文档是否一致？

把“声称的行为”和“实际代码”并排放。全仓库审查最容易漏的不是语法错误，而是
这种契约漂移：README 说 T+1，代码里却按收盘成交；文档说增量更新，实现却每次
全量重下。

### 3. 分层审查

按依赖顺序看，先底后上，避免在上层追一个其实是底层数据错误的问题：

1. 纯函数和领域规则：单位、边界、舍入、日期、空值。
2. 数据层：读取、写入、schema、主键、增量、幂等、原子性。
3. 状态机/编排层：循环、账本、失败恢复、重复执行。
4. 业务逻辑：约束、优先级、不变量、极端输入。
5. 接口层：CLI/API 参数、退出码、错误信息、序列化。
6. 报告和输出：路径、编码、空数据、NaN/Infinity、用户可读性。
7. 测试：覆盖的是行为还是实现细节，有没有盲区。
8. 文档和示例：命令、参数、前提、输出、教程顺序。

每一层都拿 `references/bug-patterns.md` 里的高发模式过一遍。不要只找“看起来
丑”的代码，优先找会产生错误结果、数据损坏、静默失败和无法复现的问题。

### 4. 把怀疑变成证据

发现可疑点后，先写最小复现，不要立刻改实现：

- 单元级：构造最小输入，断言期望行为，看它是否失败。
- 集成级：用临时目录、合成数据或 mock，跑一小段真实流程。
- 命令行级：用 `CliRunner`、临时配置或 `--help`，验证参数和输出。
- 数据级：构造两行数据足以暴露主键、排序、增量合并的问题。

复现可以是临时脚本，但修 bug 时要把关键用例沉淀成正式测试。测试要能在没有
网络、没有真实数据的情况下稳定运行。

如果无法复现，继续读调用方和数据流，确认是不是误报；仍然不确定就标成
“怀疑，未复现”，不要直接改。

### 5. 小批量修复

按风险排序，一次处理一类：

- 正确性 bug：会导致错误结果、数据损坏、静默丢数据，优先修。
- 状态和边界问题：重复执行、空输入、极端值、并发或恢复路径。
- 整洁性：死代码、未使用依赖、重复逻辑、命名误导。只做低风险清理。
- 完备性：缺失的必要功能、缺口测试、跑不通的示例。
- 文档：与代码不一致的命令、参数、路径和限制。

每批改完立刻跑相关测试和检查，再进入下一批。不要在一次提交里混入无关重命名、
格式化全仓库或依赖大升级。

修行为时要问：这个改动会不会改变已有输出、配置兼容性或用户数据？会的话在报告
里单独说明，不要藏在“小修复”里。

### 6. 检查文档、示例和依赖

- 逐条执行 README 和教程里的安全命令；参数、默认值、输出路径要和代码一致。
- 示例要能从干净环境开始，不依赖作者本地的数据、缓存或未提交文件。
- 教程要说明前置条件，例如先下载数据、先配置密钥、先启动服务。
- 删除确认未使用的依赖，更新锁文件要用包管理器，不手改。
- 检查 `.gitignore`：源码不能被忽略，数据/结果/密钥/真实持仓必须被忽略。
- 检查版本、许可证、入口点和打包配置是否仍然有效。

### 7. 最终验证

再跑一遍完整基线，加上被修 bug 的回归测试和至少一个端到端示例：

```bash
make check
uv run pytest -q
uv run python examples/offline_demo.py
git diff --check
git status --short
```

报告里写清楚每条命令的实际结果。最终结论用“已复现并修复 / 已发现但未修 /
未覆盖”，不要写“没有 bug”。

## 报告格式

先给一段结论，说明仓库整体状态和最值得注意的两三件事。然后按严重程度列：

```text
[高] path/to/file.py:123 — 一句话说明缺陷
  触发：什么输入/状态会导致什么错误结果
  证据：哪个测试或命令复现了它
  处理：已修复 / 未修，原因
  回归：新增了哪个测试
```

之后补三块：

- 已修复：按类别归纳，不必逐条重复。
- 发现但未改：说明为什么没改（超出范围、需要产品决策、无法验证）。
- 验证：命令和结果，包括没跑的检查和原因。

如果用户要的是“确保无 bug”，明确说明这不可能被证明；能承诺的是基线通过、
高发模式已检查、发现的问题有复现和回归测试。

## 边界

- 没有明确要求时，不 commit、不 push、不创建分支、不发布。
- 不删除数据、不重置 git、不改用户真实持仓或密钥文件。
- 不在审查中顺便升级大版本依赖或重写架构。
- 联网测试、真实 API 调用、耗时下载默认不做；需要时先说明代价。
- 遵守仓库自己的 `AGENTS.md`/`CLAUDE.md` 和包管理器约定。
