# 高发 bug 模式和复现思路

按“最可能造成错误结果”排序。每条给出识别信号、最小探针和修复方向。不要把它当成
必须全部命中的清单，而是审查时的联想工具。

## 1. 时间和因果

识别信号：`merge_asof`、`shift`、`rolling`、`pct_change`、日期过滤、公告日、
“最新”、缓存键里没有日期。

常见缺陷：

- 用报告期而不是公告日对齐财务数据，提前看到财报。
- 用今天的成分股、ST 名单、行业分类回填历史。
- 信号和成交在同一天完成，或成交用了当天收盘之后才知道的价格。
- 特征窗口包含当前 bar 的收盘价，但成交又在同一收盘价。
- 增量更新时用“最后日期”做闭区间，重复计算最后一天。
- 时区混用，或把交易日当自然日做偏移。
- 缓存键缺少日期/参数，换一个区间仍命中旧结果。

最小探针：

```python
# 扰动未来数据，历史输出必须完全不变
base = compute(panel)
perturbed = panel.copy()
perturbed.loc[perturbed["date"] > cutoff, "close"] *= 10
assert_frame_equal(compute(perturbed).loc[:cutoff], base.loc[:cutoff])
```

修复方向：把“可知时间”显式建模；所有 PIT 合并按公告日/可用日；增量区间用半开
区间；缓存键包含影响结果的全部参数；用测试锁住未来数据不变性。

## 2. 状态、幂等和增量

识别信号：`update`、`upsert`、`append`、`checkpoint`、`state`、`last_date`、
“断点续传”、全局可变对象。

常见缺陷：

- 重复执行追加重复行，或把已有值覆盖成空值。
- 增量只取右边界之后，漏掉左边界扩展；或只取左边界之前，漏掉右边界。
- 部分成功写入后状态已推进，下次不再重试失败部分。
- 空结果被当成“没有新数据”，也当成“应该清空旧数据”。
- 单例/模块级缓存跨请求污染。
- 失败后临时文件残留，下次被当成有效输入。
- 并发写同一文件，最后写入者覆盖别人。

最小探针：

```python
store.write(df1)
store.write(df2)          # 与 df1 有重叠主键
assert store.read() == expected_merged
store.write(df2)          # 再写一次
assert store.read() == expected_merged   # 幂等
```

修复方向：主键去重并定义覆盖规则；增量用半开区间；状态只在整批成功后推进；
写入用临时文件加原子替换；空结果和“无更新”分开表达。

## 3. 数值、单位和精度

识别信号：`* 100`、`/ 100`、`round`、`float`、`Decimal`、百分比字段、金额、
“万”“亿”、NaN 比较。

常见缺陷：

- 百分比 5% 存成 5 还是 0.05，上下游不一致。
- 金额单位是元、千元还是万元，报表和计算层不一致。
- 浮点累加导致账本差几分钱，或 `0.1 + 0.2 != 0.3` 导致断言失败。
- 先四舍五入再乘数量，和先乘再舍入结果不同。
- `NaN` 参与比较永远为假，过滤条件静默丢掉整行。
- `inf` 进入 JSON 变成 `Infinity`，标准解析器读不了。
- 负零、极大值、溢出、整数除法截断。

最小探针：用能区分单位的两个值（5 和 0.05）、一个 NaN、一个 inf、一个负数、
一个极小值，跑完整链路，看输出是否仍可解释。

修复方向：在 schema/文档里写死单位；金融金额用整数分或 Decimal；比较用
`math.isnan`/`pd.isna`；序列化前把非有限值转成 `null` 或明确报错；舍入策略
集中到一个函数并测试。

## 4. 空值和边界

识别信号：`if not df.empty`、`[0]`、`iloc[-1]`、`max()`、`min()`、`mean()`、
空列表、单元素、全 NaN。

常见缺陷：

- 空 DataFrame 被当成“清仓”或“无操作”，两种语义混用。
- 对空序列取 `[0]`、`max()`、`idxmax()` 抛异常或返回错误值。
- 单只股票、单日数据让横截面计算除零。
- 全 NaN 列通过 `dropna()` 后变成空表，后续静默跳过。
- 只有一条数据时 `pct_change` 全空，指标变成 NaN 但仍生成报告。
- 边界日（上市首日、退市日、停牌复牌日）状态判断差一天。

最小探针：为每个公共函数准备空、单元素、全 NaN、重复、乱序五组输入，断言
“要么给出明确结果，要么抛出明确异常”，不能静默产出错误值。

修复方向：显式区分“无数据”和“空目标”；入口校验最小长度；横截面计算保护
分母；报告层对 NaN 有明确展示策略。

## 5. 约束和不变量

识别信号：`clip`、`normalize`、`cap`、`limit`、权重和、现金、库存、配额、
“先应用 A 再应用 B”。

常见缺陷：

- 裁剪一个约束后破坏另一个约束，最终权重和不为 1 或超过上限。
- 先归一化再加约束，约束后没有重新归一化。
- 多个约束的优先级未定义，结果依赖字典/集合遍历顺序。
- 现金约束只检查买入，不检查费用，最终现金为负。
- 卖出数量超过可用数量，或买入后当日可卖。
- 空目标时没有按换手/仓位约束逐步退出，直接清零。

最小探针：构造同时触发两个约束的输入，断言最终结果满足所有硬约束；再构造空
目标、满仓、单票、现金不足，检查不变量。

修复方向：把约束写成有顺序的纯函数；每次裁剪后重新检查不变量；明确“硬约束
优先于目标权重”；对不可行输入抛出或返回明确状态，不要静默产出越界结果。

## 6. 连接、schema 和顺序

识别信号：`merge`、`join`、`concat`、`groupby`、`set_index`、`reset_index`、
列名映射、dtype 转换。

常见缺陷：

- 多对多连接导致行数膨胀，指标被重复计算。
- 连接键类型不一致（字符串 `"1"` 和整数 `1`），静默产生空结果。
- `merge_asof` 前没有按时间排序，抛错或结果错误。
- 用 `outer` 连接后缺失值被填成 0，制造虚假观测。
- 列名映射漏掉新字段，上游改名后静默丢列。
- 分组后顺序变化，依赖位置的下游代码取错行。
- 时区/日期类型不一致，过滤条件全部落空。

最小探针：断言连接前后行数、主键唯一性、关键列非空；用乱序输入测试
`merge_asof`；用改名/缺列输入测试 schema 校验是否报错。

修复方向：显式 schema 和 dtype；连接前校验键唯一性和类型；连接后检查行数和
空值；不要用位置索引跨分组取值。

## 7. 接口、序列化和退出

识别信号：CLI 参数、JSON 输出、`json.dump`、`ensure_ascii`、退出码、异常捕获、
`sys.exit`。

常见缺陷：

- `--start` 默认值在代码和文档里不一致。
- 参数是字符串但下游按日期/数字用，运行到一半才炸。
- 成功和失败都返回 0，脚本无法判断。
- 异常信息只打印“出错了”，没有文件、参数或原因。
- JSON 里有 NaN/Infinity、日期对象、numpy 标量，标准解析器读不了。
- HTML 报告未转义用户数据，或路径拼接导致目录穿越。
- 覆盖已有结果目录时没有提示，旧结果和新结果混在一起。

最小探针：跑 `--help` 对照文档；用非法参数、缺文件、空数据各跑一次，检查退出码
和错误信息；用严格 JSON 解析器读取输出。

修复方向：入口统一校验和类型转换；区分退出码；错误信息带上下文；序列化前做
显式转换；输出目录用 run_id 或明确覆盖策略。

## 8. 错误处理和静默失败

识别信号：裸 `except`、`except Exception: pass`、`errors="ignore"`、
`fillna(0)`、`dropna()`、默认返回空。

常见缺陷：

- 网络/解析错误被吞掉，结果少了一半数据但报告照常生成。
- 缺列时静默跳过，用户以为因子已计算。
- 失败重试没有上限或没有退避，卡死或打爆服务。
- 重试非幂等操作，重复下单/重复写入。
- 日志里记录密钥、完整请求体或个人信息。
- 异常被转成空结果，上游无法区分“没有”和“失败”。

最小探针：让依赖抛错，观察调用方是报错、重试还是静默继续；检查日志和最终输出
是否还能看出失败。

修复方向：只捕获能处理的异常；失败要么向上抛，要么记录并返回显式状态；重试
只用于幂等操作并设上限；日志脱敏。

## 9. 安全和数据卫生

识别信号：`.env`、密钥、token、真实持仓、个人数据、`subprocess`、`eval`、
`pickle`、路径拼接、HTML 模板。

常见缺陷：

- 密钥或真实账户数据被提交，或被打进报告/日志。
- 用户输入拼进 shell 命令或文件路径。
- 反序列化不可信数据（pickle、yaml.load）。
- 报告 HTML 未转义，注入脚本。
- 临时文件权限过宽，或落在共享目录。
- `.gitignore` 漏掉数据/结果目录，生成物混进版本库。

最小探针：`git status --ignored` 看被忽略项；搜索密钥模式；用包含引号/路径
分隔符的输入测试命令拼接；检查报告中的用户可控字段。

修复方向：密钥走环境变量或密钥管理；不提交真实数据；用参数列表而不是 shell
字符串；不可信输入用安全解析器；输出转义；明确忽略规则。

## 10. 测试盲区

识别信号：测试数量很少、全是大 happy path、mock 过多、条件跳过、只断言不抛异常。

常见缺陷：

- 测试只验证“能跑”，不验证数值和副作用。
- mock 掉了真正出错的层，测试通过但集成失败。
- 测试依赖当前日期、时区、随机数、网络或执行顺序。
- 断言浮点数用 `==`。
- 只测正常输入，空/边界/重复执行没有覆盖。
- 测试文件没有被收集（命名、路径、依赖缺失）。
- 覆盖率很高但关键分支没测。

最小探针：给核心函数加一个空输入、一个边界、一个重复执行；把系统时间/随机种子
固定；用 `pytest --collect-only` 确认测试真的被收集。

修复方向：测行为和不变量，不测实现细节；关键路径加集成测试；固定时间和随机；
浮点用近似；对静默跳过加断言。

## 11. 文档、配置和依赖漂移

识别信号：README 命令、配置样例、默认值、版本号、锁文件、未使用依赖。

常见缺陷：

- README 的参数名、默认值、输出路径和代码不一致。
- 配置样例缺必填项，或包含已删除的键。
- 文档说“默认不联网”，测试却依赖网络。
- 删了代码但依赖还在，或用了依赖但没声明。
- 锁文件和 `pyproject.toml`/`package.json` 不同步。
- 示例依赖作者本地数据或未提交文件。

最小探针：逐条执行文档命令；用最小配置启动；用 `rg` 查依赖是否被导入；在干净
环境安装并跑示例。

修复方向：文档跟代码同批改；配置用 schema 校验；依赖删除后更新锁文件；示例
自带合成数据或明确下载步骤。

## 12. 性能和资源

识别信号：循环里查数据库、重复读大文件、无界缓存、一次性加载全市场、递归、
大对象复制。

常见缺陷：

- 每个标的重复读同一个 parquet，I/O 成为瓶颈。
- 在循环里做全表过滤/排序，复杂度爆炸。
- 缓存无上限，长期运行内存泄漏。
- 一次性把多年全市场数据读进内存。
- 文件句柄、数据库连接、线程池没有关闭。

最小探针：用缩小版数据计时，观察随规模增长的趋势；用 `tracemalloc` 或
`resource` 看内存；重复调用看缓存是否增长。

修复方向：批量读取、向量化、索引/分区；缓存设上限和失效；资源用上下文管理器；
先测量再优化，不要凭感觉重写。

## 13. 量化/回测专项

这一节假设仓库做 A 股或类似市场的研究/回测。没有相关代码就跳过。

### 时间契约和未来函数

- 信号是否只使用 T 日收盘及之前的数据，成交是否在 T+1。
- 财务数据是否按公告日可用，而不是报告期。
- 股票池是否 PIT：上市、退市、ST、停牌、指数成分都不能用今天的名单回填。
- 因子窗口是否包含当前 bar 的收盘，而成交又用同一价格。
- walk-forward 的参数是否只在训练窗选择。
- 样本外是否被反复用来调参后重报。

探针：扰动未来价格/财务数据，历史信号和净值必须完全不变；把公告日推迟一天，
当天及之前的因子值不能变。

### 复权和公司行动

- 用后复权还是前复权，是否每次从原始价乘因子重算。
- 复权因子变更后，历史缓存是否失效。
- 分红、送转、拆股是否造成价格跳变和虚假收益。
- 成交量是否也需要复权，单位是否一致。
- 停牌期间价格如何估值，复牌首日收益是否被错误计算。

探针：构造一次除权，手工算复权前后收益；对比复权因子跳变前后的价格连续性。

### 成交规则

- T+1：当日买入不可卖，账本是否记录可卖日期。
- 整手：买入是否向下取整，卖出零股是否允许，科创板/北交所最小数量是否不同。
- 涨跌停：是否用原始价和分位计算，涨停不买、跌停不卖，一字板是否处理。
- 停牌：不可买不可卖，持仓如何估值，订单是否记录跳过原因。
- 退市：持仓能否退出，最后价格如何处理。
- 流动性：单日成交是否超过 ADV 的限制。

探针：构造涨停/跌停/停牌/一字板/零股/不足一手，逐条断言成交或跳过。

### 成本和资金

- 佣金双边、最低佣金、印花税卖出单边、过户费、滑点是否都计入。
- 费率是否按日期变化，历史回测是否用了当前费率。
- 现金是否可能为负，买入是否预留费用。
- 小额交易的最低佣金是否被忽略。
- 换手和成本拖累的定义是否一致。

探针：手工算一笔买入和一笔卖出的费用，和账本对比；用小资金触发最低佣金。

### 基准和指标

- 基准是否和策略使用同一区间、同一交易日历。
- 基准缺失日期是否被前向填充，制造虚假超额。
- 超额收益是否在共同区间计算，年化是否用对天数。
- 夏普、最大回撤、换手、成本拖累的定义是否写清楚。
- 分红是否计入基准，是否注明价格指数和全收益指数的差异。

探针：构造基准缺一天的数据，检查对齐和超额；手工算一段净值的最大回撤和年化。

### 组合约束

- 单票/行业上限、现金底线、换手上限、回撤降仓是否都是硬约束。
- 约束冲突时的优先级是否稳定。
- 空目标是否按约束逐步退出，而不是直接清零。
- 权重和是否为 1，现金是否非负。
- 行业分类缺失时是否被当成一个行业，导致约束偏松或偏紧。

探针：构造同时触发多个约束的输入，断言最终权重满足所有硬约束；构造空目标和
满仓，检查退出路径。

### 验证关卡

- IS/OOS 划分是否按日历，而不是随机打乱。
- walk-forward 是否有重叠或泄漏。
- 成本敏感性是否真的把全部成本乘倍，包括最低佣金。
- 参数网格是否只在样本内跑，试验次数是否登记。
- 过拟合门槛是否可配置、是否有测试。
- 试验登记是否会被并发写坏，是否可复现。

探针：构造一个明显过拟合的参数网格，验证关卡是否标红；重复跑同一配置，检查
registry 是否重复计数。

## 严重程度和取舍

- 高：错误结果、数据损坏、静默丢数据、资金/安全风险、无法复现。必须修或明确
  阻止发布。
- 中：特定边界才触发、错误信息误导、状态不一致、重要测试缺失。计划修。
- 低：命名、重复代码、文档小错、非关键性能。可批量清理。
- 怀疑：无法复现或依赖未确认的前提。只报告，不改。

判断是否值得修，问三个问题：真实场景会不会触发？触发后用户能不能发现？修复
会不会引入更大兼容性风险？三个都偏向“是/不能/不会”时，优先级高。
