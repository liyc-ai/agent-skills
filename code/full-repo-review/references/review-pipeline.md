# 审查流水线细节

这份参考按阶段展开，适合标准或深度审查。仓库很小时只取需要的部分，不要为了走流程
而走流程。

## 阶段 0：范围和验收

把下面几项写成四五句话，必要时贴给用户确认：

```text
范围：src/、tests/、examples/、README；不看 infra/ 和第三方 vendored 代码。
基线：make check、pytest、examples/offline_demo.py。
深度：只读审查 + 修复高置信度正确性问题；不重构架构。
限制：不联网，不跑真实数据下载，不提交。
完成标准：基线通过；每个修复有回归测试；文档命令可复现。
```

深度可以分三档：

- 快速：跑基线、读入口和核心模块、查高发模式。适合小仓库或发布前冒烟。
- 标准：完整分层、契约对照、示例执行、修复高置信度问题。默认用这档。
- 深度：加数据流追踪、边界矩阵、失败恢复、并发/幂等、性能热点。适合核心
  基础设施或资金相关代码。

## 阶段 1：仓库侦察

先收集形状，不评价：

```bash
git status --short
git log --oneline -10
find . -maxdepth 2 -type f \
  -not -path './.git/*' \
  -not -path './node_modules/*' \
  -not -path './.venv/*' | sort | sed -n '1,200p'
```

然后看这几类文件：

- 入口：`README`、`Makefile`、`pyproject.toml`、`package.json`、`Cargo.toml`、
  `go.mod`、CI 配置。
- 约束：`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING`、`docs/`、`LICENSE`。
- 运行：测试目录、fixtures、示例、脚本、配置样例。
- 风险：`.env*`、凭据文件、真实数据、生成物、被忽略的源码目录。

做一个模块依赖草图，哪怕只是缩进列表：

```text
cli -> pipeline -> strategy -> portfolio -> broker
                   \-> data -> provider
reporting <- pipeline
```

依赖方向不对，往往就是隐藏耦合和测试困难的来源。

## 阶段 2：基线检查

不要假设检查命令。先从 README、Makefile、CI 里找仓库认可的命令，再执行。

### Python

```bash
uv sync --all-extras           # 或 poetry install / pip install -e '.[dev]'
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest -q
```

没有 uv 时用仓库已有的虚拟环境和命令。注意 `pytest` 配置里的默认 `-m`、覆盖率
门槛和 `addopts`，它们会改变“通过”的含义。

### Node / TypeScript

```bash
npm ci
npm run lint
npm run typecheck
npm test -- --run
npm run build
```

### Rust / Go / Java / .NET

```bash
cargo test && cargo clippy --all-targets -- -D warnings
go test ./... && go vet ./...
./gradlew test check          # 或 mvn verify
dotnet test && dotnet build
```

### 基线记录表

在草稿里记，不要往仓库塞临时文件：

```text
命令 | 结果 | 备注
ruff | pass |
mypy | fail: 3 errors in X | 既有问题，未修
pytest | 42 passed, 3 skipped | 跳过的是 network
demo | fail: 缺 fixtures | 环境问题，需确认
```

“通过”也要追问：测试是不是只覆盖了 happy path，关键模块有没有测试，跳过的是
不是核心路径。

## 阶段 3：契约映射

对每个模块写一行契约，格式是“输入 -> 输出，前提/副作用”：

```text
load_prices(symbol, start, end) -> DataFrame[date, ohlcv]
  前提：本地有数据；输出按日期升序、无重复；不修改磁盘。
rebalance(targets, holdings) -> orders
  前提：targets 是权重；输出先卖后买；现金不能为负。
```

重点对照这些地方：

- README/教程承诺的命令、参数、默认值。
- 配置 schema 和实际读取的键。
- 数据字典和实际列名、dtype、单位。
- 公开 API 的异常类型和返回结构。
- 报告里的指标定义和实现。
- 示例使用的路径、文件名和数据前提。

契约不一致有三种处理：代码错就改代码；文档旧就改文档；双方都有理但需要产品
决策，就报告并让用户选，不要擅自改语义。

## 阶段 4：分层检查

### 纯函数和领域规则

- 单位：百分比是 5 还是 0.05，金额是元还是分，收益率是小数还是百分数。
- 边界：0、负数、空集合、单元素、极大值、NaN/Infinity。
- 舍入：金融金额用十进制还是浮点，先乘后除还是先除后乘。
- 日期：时区、闭开区间、交易日和自然日、月底/年末。
- 规则优先级：多个限制同时触发时，哪个先裁剪，是否可能互相打架。

### 数据层

- schema 是否显式，缺列/多列/类型变化是否报错而不是静默继续。
- 主键和去重：重复写入是覆盖、追加还是报错。
- 增量：左边界、右边界、重叠区间、空增量、重复执行。
- 原子性：写一半失败会不会留下半个文件；临时文件是否清理。
- 排序和索引：合并前是否排序，`merge_asof` 的前置条件是否满足。
- 缺失值：缺数据是跳过、填零还是前向填充；填充是否会制造虚假观测。
- 缓存：键是否包含所有影响结果的参数；失效策略是否正确。

### 状态机和编排层

- 循环的初始状态、终止条件、空迭代。
- 账本不变量：现金、持仓、市值、费用是否始终自洽。
- 重复执行：同一输入跑两次结果是否一致。
- 失败恢复：中途异常后能否续跑，状态是否可重建。
- 顺序依赖：先卖后买、先更新后计算、先校验后写入。
- 并发：共享状态是否有锁，文件写入是否可并行。

### 业务逻辑

- 约束是否真的硬约束，裁剪后会不会再次越界。
- 空目标、全清仓、单票、满仓、现金不足等边界。
- 优先级：多个约束冲突时的处理顺序是否合理且稳定。
- 不变量：权重和、现金底线、行业上限、换手上限。
- 极端市场：涨跌停、停牌、退市、缺失价格、停牌复牌。

### 接口层

- 参数默认值、必填/可选、类型转换和校验。
- 退出码：成功、参数错误、数据错误、外部服务错误是否区分。
- 错误信息：是否包含定位信息，是否泄露密钥。
- 输出：stdout/stderr 分工，机器可读格式是否稳定。
- 序列化：NaN/Infinity、日期、枚举、空值、编码。
- 兼容性：旧配置、旧数据、旧命令行是否还能用。

### 报告和输出

- 空数据、全 NaN、单点数据是否还能生成。
- 数值格式：单位、精度、百分号、货币符号。
- 文件路径：相对/绝对、目录不存在、覆盖行为。
- HTML/JSON/CSV：转义、编码、严格 JSON、注入风险。
- 报告结论是否超出数据支持范围。

### 测试

- 测试的是行为还是实现细节；重命名内部函数会不会全挂。
- 关键边界是否有测试：空、零、负、单元素、重复、乱序。
- 是否有“未来数据扰动”测试，防止时间泄漏。
- 是否有幂等/重复执行测试。
- network、slow、integration 标记是否真的隔离。
- fixtures 是否真实到能暴露 schema 问题，还是过度 mock。
- 测试是否可能静默跳过（缺依赖、缺数据、条件判断写错）。

### 文档和示例

- 命令能否直接复制执行，参数名和默认值是否对。
- 是否说明前置条件：依赖安装、数据下载、密钥、服务启动。
- 教程顺序是否自洽：先下载再回测，先生成再查看。
- 输出路径和报告位置是否和代码一致。
- 示例是否依赖作者本地文件或未提交数据。
- 限制和免责声明是否还在，是否被新功能冲掉。

## 阶段 5：证据协议

每个发现至少要有其中一种证据：

1. 失败测试：最小输入、明确期望、当前失败。
2. 命令输出：CLI/脚本的实际错误或错误结果。
3. 数据对照：两行数据或小表证明合并、排序、单位错误。
4. 不变量检查：账本、权重和、现金等断言失败。
5. 代码路径证明：无法运行时，给出完整调用链和触发条件，标为未复现。

不要用“这里可能有问题”作为结论。要么复现，要么明确降级为怀疑。

写复现时控制变量：

- 固定随机种子。
- 用临时目录，不污染仓库。
- 用合成数据，不依赖网络。
- 只保留触发问题所需的最小字段和行数。
- 先确认测试在旧代码上失败，再修。

## 阶段 6：修复批次

建议批次顺序：

1. 会导致错误结果或数据损坏的正确性 bug。
2. 静默失败、状态不一致、幂等和恢复问题。
3. 边界和输入校验。
4. 低风险整洁性清理。
5. 缺口测试和文档同步。

每批的节奏：

```text
选一个主题 -> 写/改测试 -> 看它失败 -> 最小实现 -> 跑相关测试
-> 跑全量检查 -> 记录 -> 下一批
```

修复时注意：

- 不要为了过测试而改测试期望，除非原期望本身就是错的，并在报告里说明。
- 不要顺手改公共 API 的名字或返回类型。
- 不要把一个 bug 修成两个新特性。
- 行为变化要单独列出，尤其是默认值、排序、异常类型、输出格式。
- 文档和注释只改与本次行为相关的部分。

## 阶段 7：完备性检查

“功能完备”不是“文件齐全”，而是用户能按文档完成主要任务。逐条走：

- 安装：干净环境能否安装，锁文件是否一致。
- 配置：最小配置能否启动，错误配置是否有清晰报错。
- 主流程：一条命令能否从输入到输出。
- 边界流程：空数据、缺文件、外部服务失败。
- 恢复流程：中断后能否继续，重复执行是否安全。
- 输出：结果文件是否齐全、可读、可复现。
- 示例：至少一个离线示例，一个真实/集成示例。
- 文档：快速开始、配置说明、数据字典、限制说明。
- 清理：临时文件、缓存、日志、生成物是否有明确位置和忽略规则。

对每个缺口判断：是必须现在补，还是记录为后续工作。不要把所有“可以更好”都
当成 bug。

## 阶段 8：收尾验证

最终至少跑：

```bash
# 仓库原有完整检查
make check

# 针对修复的测试
uv run pytest tests/unit/test_x.py -q

# 端到端
uv run python examples/offline_demo.py

# 工作区状态
git diff --check
git status --short
```

如果某项没跑，写清楚原因：需要网络、需要真实数据、耗时过长、环境缺失。不要
用“应该没问题”替代结果。

## 按仓库类型的入口

### 库/SDK

先看公开 API 和版本兼容，再看内部实现。重点：导出列表、类型标注、异常契约、
依赖范围、向后兼容、文档示例。

### CLI 工具

先跑 `--help` 和最小命令，再看参数解析、退出码、错误信息、文件副作用。重点：
默认值、路径处理、覆盖行为、管道输出、信号处理。

### Web 服务

先看路由、鉴权、输入校验、错误处理，再看数据层。重点：注入、越权、超时、
重试、幂等、事务边界、日志脱敏。

### 数据/回测/量化

先看时间契约和数据 PIT，再看撮合和账本，最后看指标和报告。重点：未来函数、
复权、停牌/涨跌停、成本、整手、基准对齐、样本内外泄漏。详见
[bug-patterns.md](bug-patterns.md) 的量化专项。

### 前端

先跑构建和类型检查，再看数据流和状态。重点：加载/空/错误状态、竞态、内存
泄漏、可访问性、XSS、依赖体积。

## 常见误判和取舍

- 代码丑不等于有 bug。整洁性问题单独归类，不要和正确性混在一起。
- 测试没覆盖不等于实现错。先复现，再决定是否补测试。
- 文档旧不等于代码错。确认哪个是当前契约，再改对应的一侧。
- 边界情况多不等于都要处理。判断它是否可能真实发生，以及失败是否安全。
- 依赖旧不等于必须升级。审查阶段只处理确认未使用或有已知风险的依赖。
- 静态检查全绿不等于正确。类型检查覆盖不到业务不变量和时间语义。
